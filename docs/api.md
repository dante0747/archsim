# HTTP API (v1)

Base path: `/api/v1`. JSON uses camelCase. The API is local and single-user: there is no
authentication (see [SECURITY.md](../SECURITY.md)).

- OpenAPI document: `GET /api/v1/openapi.json`
- Interactive docs: `GET /api/v1/docs`

## Errors

Domain errors use one shape:

```json
{
  "detail": {
    "message": "Cannot simulate: Redis Cache can miss (hit ratio 80%) but nothing reads the data on a miss: ...",
    "issues": [
      {
        "severity": "error",
        "code": "cache.miss_unrouted",
        "message": "Redis Cache can miss (hit ratio 80%) but nothing reads the data on a miss: its 'miss' port is not connected and API Servers has no link set to 'Reads only on a cache miss'.",
        "nodeId": "cache",
        "edgeId": null,
        "path": null,
        "hint": "Cache-aside: give the service a link to the database with 'Reads only on a cache miss' on. Read-through: connect the cache's 'miss' port to the database."
      }
    ]
  }
}
```

| Status | When |
| --- | --- |
| 400 | Contradictory request (e.g. both `document` and `exampleId`). |
| 404 | Unknown project, run or example. |
| 409 | Revision conflict on save; report requested for an unfinished run; comparing unfinished runs. |
| 413 | Request body larger than `ARCHSIM_MAX_BODY_BYTES`. |
| 422 | Document invalid (with `issues`), run too large, a calibration that cannot be done, or FastAPI request validation errors (FastAPI's standard `detail` list). |

## Meta

| Method | Path | Description |
| --- | --- | --- |
| GET | `/health` | `200 {"status": "ok", "database": "ok"}`; `503 {"status": "degraded", "database": "unavailable"}` when the database cannot be reached, so health checks take the instance out of service. |
| GET | `/meta` | Engine/schema/report versions, database dialect, run limits. |
| GET | `/pricing` | Price sources a design can name in `pricing`: `generic` (illustrative rates) and every price snapshot on this machine (`provider`, `region`, `date`, `file`, `sha256` of its content, `newest` for the newest of its provider and region). A design pins one with `pricing.snapshotDate`. See [pricing.md](pricing.md). |
| GET | `/components` | Component catalog: ports, field descriptors (kind, unit, range, group, assumption flag, visibility), defaults, modeled/not-modeled notes, presets (with `tier` and `sources`, the links behind documented preset numbers), `technologyTraits`, `technologyDefaults`, `technologySources` (links behind documented defaults) and `technologyTiers` (core or experimental); plus `edgeFields`, `workloadFields` and `tierNote` (the text of the "experimental" badge). |
| GET | `/schema/architecture` | JSON Schema of the document. |
| GET | `/examples` | Bundled example documents (id, name, description, tags, scenario count). |
| GET | `/examples/{exampleId}` | One example document. |
| POST | `/validate` | Body `{document, scenarioId?}`. Returns `{valid, issues[]}`; never saves or simulates. |
| POST | `/export` | Body `{document, format: "compose" | "k8s" | "mermaid"}`. Returns `{format, text, suffix, mediaType}`: scaffolding generated by the engine (empty specs filled with its auto sizes), the same exporters the MCP server uses. |
| POST | `/import` | Body `{format: "compose" | "k8s" | "terraform", text, name?}` (Terraform: the JSON of `terraform show -json`). Returns `{document, report}`; the report lists `mapped`, `guessed`, `ignored`, `suggestions` (links to confirm) and validation `issues`. Nothing is stored. 422 when the text cannot be read as that format. See [import.md](import.md). |
| POST | `/calibrate` | Body `{document, source: "prometheus" | "otlp", mapping (YAML text or object; a string is always the mapping's text, never a path: the API reads no files), prometheusUrl or recorded (recorded responses), range ("START/END"; a recording uses its own; no offset means UTC), step (default: the mapping's), traces (OTLP JSON), replay}`. Sets inputs from telemetry and replays the observed traffic; returns `{document, changes, notes, calibration, summary}` (the stored project is not changed; `summary` gives the end-to-end p95 and the largest of all replay errors). 422 when the document, mapping or telemetry cannot be used, when Prometheus fails (unreachable, over the deadline `ARCHSIM_PROMETHEUS_TIMEOUT_S` (30 s, body included), over `ARCHSIM_PROMETHEUS_MAX_BYTES` (50 MiB), a cut-off or non-Prometheus answer, a host outside `ARCHSIM_PROMETHEUS_ALLOWED_HOSTS`), and when the replay run would exceed `ARCHSIM_MAX_REQUESTS` or `ARCHSIM_CALIBRATE_MAX_WALL_SECONDS` (60 s; the replay runs inside the request). Error messages name what is wrong and where, never the values sent or what the Prometheus server answered. The API queries the Prometheus URL it is given: keep it on localhost, and set `ARCHSIM_PROMETHEUS_ALLOWED_HOSTS` (comma-separated `host` or `host:port`) before it is reachable from anywhere else. See [calibration.md](calibration.md). |
| POST | `/analyze` | Body `{document, scenarioId?}`. Returns what a run would use, computed by the engine without simulating: `sizing` (per part: `specs` simulated with their `source` set/auto/scenario, `auto` sizes, `peakRps`, `why`, `pricePerHour`, `sku` with a price snapshot), `cost` (monthly estimate by part; each line's `priceSource` is `set` (by the user), `snapshot` (with `sku` and `snapshotDate`), `preset` (a technology preset's illustrative price), `size` or `default`; `pricing` names the source, with the snapshot's `sha256`), `review` (design review findings), `reviewCounts`, `reviewRules`, `peakRps`, `technologies` (each part's technology and tier), `inputs` (every performance input with its value and provenance: `measured`, `documented`, `assumed` or `illustrative`), `provenanceCounts`, `calibration`, `estimate` (what queueing formulas predict at the peak, without simulating: utilization and wait per part, the busiest part, a mean and a rough p95 latency, or where it saturates) and `confidence` (`level` high/medium/low, `reason`, `reasons`, `drivers`, `howToRaise`; parts weighted by their estimated utilization). See [simulation-model.md](simulation-model.md#confidence-confidence). 422 with `issues` when the document cannot be read. The web app calls it with live validation; `archsim analyze` prints the same. |

## Projects

| Method | Path | Description |
| --- | --- | --- |
| GET | `/projects` | List (most recently updated first) with node and scenario counts. |
| POST | `/projects` | Create from `{document}`, `{exampleId}`, or blank. Optional `name`, `description`. `201`. With `{exampleId, reuseUnedited: true}` and no `name`, returns the most recent copy of that example that was never saved and still matches it (`200`) instead of creating another; the web app opens templates this way. |
| POST | `/projects/import` | Body: a raw document (older schema versions are migrated). Optional `?name=`. `201`. |
| GET | `/projects/{id}` | Project with its document and `revision`. |
| PUT | `/projects/{id}` | Body `{name?, description?, document?, expectedRevision?}`. Increments `revision`; `409` if `expectedRevision` is stale. |
| DELETE | `/projects/{id}` | Deletes the project and its runs. `204`. |
| POST | `/projects/{id}/duplicate` | Copy as "Name (copy)". `201`. |
| GET | `/projects/{id}/export` | The document as a download (`Content-Disposition: attachment`). |

Saving accepts documents that are *schema-valid* even if graph validation fails (for example a
dangling cache miss port), so work in progress can be stored. Simulation requires a fully valid
document. Schema-invalid documents (unknown keys, out-of-range link settings, wrong
`schemaVersion`) are rejected with `422`. The project name is authoritative and is copied into
`document.metadata.name`.

## Runs

| Method | Path | Description |
| --- | --- | --- |
| POST | `/projects/{id}/runs` | Body `{scenarioId?, label?, document?}`. Validates, then enqueues. `202` with the run. `document` simulates unsaved edits; it is stored with the run. |
| POST | `/projects/{id}/runs/batch` | Body `{scenarioIds: [..], document?}` (1-10 entries; `null` = base document). Validates all before enqueueing any. `202` with a list. |
| GET | `/projects/{id}/runs` | Recent runs (newest first, up to `ARCHSIM_RUN_HISTORY_LIMIT`, default 200), without reports. |
| GET | `/runs/{runId}` | Status, `progress` (0-1), `error`, seed, digests, and a small `summary` once finished. Poll this. |
| GET | `/runs/{runId}/report` | Full report (`409` unless `succeeded`). See below. |
| GET | `/runs/{runId}/input` | The exact document submitted for the run (re-importable). |
| POST | `/runs/{runId}/cancel` | Cancels a queued run immediately. A running one is stopped by the worker holding it, on any instance, within about 2 s (its next heartbeat; at once when that worker is in the same process); one still going `ARCHSIM_CANCEL_GRACE_SECONDS` (10 s) later is killed. The response shows `cancelled`, or `running` while the cancel is on its way. |
| POST | `/runs/{runId}/rerun` | Re-simulates the stored input with the same scenario and seed. Response has `reproducesRunId`; compare `resultDigest` values. `202`. |
| DELETE | `/runs/{runId}` | Cancels if active, then deletes. `204`. |

Run `status`: `queued`, `running`, `succeeded`, `failed`, `cancelled`. A failed run has
`error.message` and, for document problems, `error.issues`. `progress` is read from the
database, where the worker simulating the run writes it at most once a second, so every API
instance reports the same value.

### Background runs and several instances

Runs are queued in the database; workers take them. By default `archsim-api serve` contains a
worker (`ARCHSIM_EMBEDDED_WORKER=true`), so one command runs everything. Each run simulates in a
process of its own (`ARCHSIM_RUNNER=process`), up to `ARCHSIM_MAX_CONCURRENT_RUNS` at once
(default: CPU count - 1).

- **Restarts.** An API or worker that stops normally (Ctrl+C, SIGTERM) gives its runs back to the
  queue, and the next worker simulates them again from the start. One that dies without warning
  (killed, out of memory, host lost) stops renewing its runs' leases; after
  `ARCHSIM_LEASE_SECONDS` (30 s) another worker, or the same API after a restart, requeues them.
  A run whose worker stops twice is `failed` with "The simulation worker stopped
  unexpectedly…".
- **A crashed simulation** (its process ran out of memory or was killed) fails only that run,
  with the same message; the worker and its other runs carry on.
- **Deadline.** A run still going `ARCHSIM_MAX_WALL_SECONDS` + 30 s after it started is killed and
  `failed`, even if the simulation stopped checking its limits.
- **Several instances.** With PostgreSQL, any number of API instances and workers can share one
  database: workers claim runs with `FOR UPDATE SKIP LOCKED`, and cancel requests reach the
  worker holding a run wherever it is. Run extra workers with `archsim-api worker --slots N`
  (`docker compose --profile workers up --scale worker=2`), and set
  `ARCHSIM_EMBEDDED_WORKER=false` on API instances that should only serve HTTP. Hosts need
  synchronised clocks (NTP): leases compare their times. SQLite works for several processes on
  one machine only.
- **Migrations** take a PostgreSQL advisory lock, so instances starting together migrate one at
  a time. `archsim-api migrate` (the Compose `migrate` service) migrates once and exits; then
  set `ARCHSIM_AUTO_MIGRATE=false` on the instances.
- **Workers table.** `job_workers` lists each worker's latest heartbeat (every 2 s), slots and
  runs in flight; rows of workers gone for an hour are deleted.

### Report shape

```
{
  "reportVersion": "1.13",
  "window":     { "warmupS", "durationS", "measuredS", "drainS", "simulatedS" },
  "summary":    { "offeredRps", "throughputRps", "successRate", "latencyMs": {p50, p95, ...},
                  "latencyWithFailuresMs", "latencyByOp", "failureBreakdown": [...],
                  "accounting": {...}, ... },
  "timeseries": { "bucketS", "t": [...], "offeredRps", "throughputRps", "errorRps",
                  "timeoutRps", "attemptRps", "latencyP50Ms", "latencyP95Ms", "latencyP99Ms" },
  "nodes":      [ { "id", "type", "label", "status", "statusReasons", "summary", "accounting",
                    "timeseries": { "utilization", "queueMean", ... }, "config" } ],
  "edges":      [ { "id", "source", "target", "callRps", "retries", "timeouts", ... } ],
  "findings":   [ { "severity", "kind", "nodeId", "title", "detail", "suggestion"?, "evidence" } ],
  "assumptions":{ "modelNotes", "technologies", "userInputs", "provenanceCounts", "calibration",
                  "components", "validationWarnings" },
  "sizing":     { "auto", "targetCpuUtilization", "nodes": { id: { "specs", "auto", "why", ... } } },
  "cost":       { "monthly", "perMillionRequests", "byNode": [...], "notes", "hasCost", ... },
  "review":     [ { "severity", "rule", "title", "detail", "suggestion", "nodeIds", "edgeIds" } ],
  "estimate":   { "method", "atRps", "latencyMs": {mean, p95}, "busiest", "overloaded",
                  "saturationRps", "summary", "paths", "breakdown", "parts": [...], "notes" },
  "confidence": { "level", "reason", "reasons", "drivers": [...], "weightedBy", "howToRaise" },
  "input":      { resolved document that was simulated (auto sizes filled in) },
  "provenance": { "engineVersion", "schemaVersion", "seed", "scenarioId", "scenarioName",
                  "overrides", "inputDigest", "resultDigest", "requestsGenerated",
                  "eventsProcessed", "wallSeconds", "python", "simpy" }
}
```

Metric definitions are in [`simulation-model.md`](simulation-model.md#measurement-window-and-metric-definitions);
`confidence` and `estimate` (report 1.13+) in its [Confidence](simulation-model.md#confidence-confidence)
and [Instant estimate](simulation-model.md#instant-estimate-estimate) sections. Neither is part of
`resultDigest`, which covers `summary`, `timeseries`, `nodes`, `edges` and `window`.

## Compare

| Method | Path | Description |
| --- | --- | --- |
| GET | `/compare?a={runId}&b={runId}` | Both runs must have succeeded. Returns `labels`, `provenance`, `inputDiff` (path, label, a, b), `kpis` (value, delta, relative delta, verdict better/worse/same), per-node rows, `bottleneck` for each run, `explanations`, `warnings` (different seeds or engine versions) and both time series. |

## Walkthrough with curl

```bash
API=http://127.0.0.1:8000/api/v1
wait_run() {  # poll until the run leaves queued/running
  while :; do
    s=$(curl -s "$API/runs/$1" | jq -r .status)
    [ "$s" = queued ] || [ "$s" = running ] || break
    sleep 1
  done
  echo "$1: $s"
}

# 1. Create a project from the starter example
PID=$(curl -s -X POST $API/projects -H 'content-type: application/json'   -d '{"exampleId": "cache-aside-starter"}' | jq -r .id)

# 2. Run two scenarios (returns immediately with status "queued")
A=$(curl -s -X POST $API/projects/$PID/runs -H 'content-type: application/json'   -d '{"scenarioId": "one-api-replica"}' | jq -r .id)
B=$(curl -s -X POST $API/projects/$PID/runs -H 'content-type: application/json'   -d '{"scenarioId": "three-api-replicas"}' | jq -r .id)

# 3. Poll until finished
wait_run $A; wait_run $B
curl -s $API/runs/$A | jq '{status, summary}'

# 4. Fetch the full report and its findings
curl -s $API/runs/$A/report | jq '.findings[] | {severity, title}'

# 5. Compare the two runs
curl -s "$API/compare?a=$A&b=$B" | jq '{inputDiff, explanations}'

# 6. Reproduce run A from its stored input and seed
R=$(curl -s -X POST $API/runs/$A/rerun | jq -r .id)
wait_run $R
curl -s $API/runs/$R | jq -r .resultDigest
curl -s $API/runs/$A | jq -r .resultDigest      # same value

# 7. Export and re-import
curl -s $API/projects/$PID/export -o starter.archsim.json
curl -s -X POST $API/projects/import -H 'content-type: application/json'   --data-binary @starter.archsim.json | jq '{id, name}'
```

## Stability

Paths are versioned (`/api/v1`). Breaking changes will go to `/api/v2`. Reports carry
`reportVersion` and documents carry `schemaVersion`.
